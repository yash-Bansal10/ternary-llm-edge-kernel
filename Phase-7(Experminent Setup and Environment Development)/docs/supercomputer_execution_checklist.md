## Part 1: The Supercomputer Strategy: Pitfalls & Proper Usage

Having access to a supercomputer is an incredible asset for dealing with the massive memory footprints of Large Language Models, but it requires a careful, highly intentional scientific approach to ensure your results remain strictly relevant to **Edge AI**.

### The Hardware Trap
*   **The Problem:** Your research is focused on **Edge AI** (smartphones, microcontrollers, IoT devices), which suffer from severe power constraints, tiny caches, and limited ALU (math) capabilities. A supercomputer is the exact opposite—it features massive AVX-512 vector registers, enormous L3 caches (often Gigabytes), and extreme memory bandwidth.
*   **The Risk:** If you simply compile your C++ benchmarking script and run it natively on the supercomputer's CPUs, your latency numbers will be **scientifically invalid** for your paper. The supercomputer's massive pipelines will brute-force the unpacking math so efficiently that it completely hides the "Unpacking Tax" and "ALU Underutilization" bottlenecks that plague weak edge devices. 

### The Correct Usage (How to rigorously use the Supercomputer)
You must treat the supercomputer as a massive "Preparation and Simulation" engine. Here is *every* correct way to use it for this project:

1.  **Downloading & Storing Base LLMs:** Modern open-source LLMs like LLaMA-3 8B or Mistral 7B are massive. A standard 8-billion parameter model in FP16 (16-bit floating point) takes up roughly **16 Gigabytes** of disk space just to store. Supercomputers have terabytes of dedicated scratch storage and fiber-optic internet to pull these models from HuggingFace in seconds.
2.  **The Ternary Quantization Pipeline (PTQ/QAT):** Processing a 16GB model to find the optimal scaling factors and converting every single weight from FP16 down to Ternary `{-1, 0, 1}` is incredibly RAM-intensive. A standard laptop will crash attempting Post-Training Quantization (PTQ) on an 8B model. You will use the supercomputer's massive RAM (often 64GB to 256GB+) and parallel CPU cores to run the Python quantization scripts without out-of-memory errors.
3.  **Cycle-Accurate Hardware Simulation:** Since you cannot benchmark natively on the supercomputer, you will install a Cycle-Accurate Hardware Simulator like `gem5` or `QEMU`. These programs create a perfect, virtualized sandbox of a weak edge chip (like an ARM Cortex-M microcontroller). Simulating an edge device cycle-by-cycle is highly computationally expensive; it might take a supercomputer an hour to simulate just a few seconds of an edge device's real-time execution. This is the ultimate, scientifically valid use of your supercomputer access.

### Strategy for your 16GB Pendrive
Because a raw FP16 8-billion parameter LLM is roughly 16GB, **it will not fit on your pendrive** alongside the OS hidden files, your scripts, and output data. Here is exactly how to use your pendrive:
*   **Rule 1:** Do **not** try to store or transport the raw, unquantized FP16 LLM weights on your pendrive. Leave the heavy FP16 files permanently stored on the supercomputer's internal storage.
*   **Rule 2:** Run the ternary quantization script on the supercomputer. Because you are compressing the weights to 1.58 bits, that massive 16GB file will shrink down to approximately **1.58 GB**.
*   **Rule 3:** Your 16GB pendrive is perfect for transporting the **Final Deliverables**. You will use it to store:
    *   The highly compressed **Ternary Weights** (~1.58 GB).
    *   Your PyTorch C++ Extension source code.
    *   The `csv` log files generated by the `gem5` hardware simulator.
    *   The exact scaling factors and tensor dimensions needed for your research paper.

## Part 2: Software Deployment: The PyTorch Custom Extension

To make this research highly impactful and easily testable on full LLMs, we will not leave the code as a standalone C++ script. 
*   **The Goal:** Package the C++ code as a **PyTorch Custom C++ Operator**.
*   **Why?** By wrapping our ultra-fast C++ hardware logic into PyTorch, anyone in the world can run `pip install ternary-edge-mac`. Inside normal Python code, researchers can then simply type `output = ternary_edge.linear(weights, activations)`. Bridging the gap between low-level hardware optimization and Python's ease-of-use significantly increases the paper's value and citation potential.
